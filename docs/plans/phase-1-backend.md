# Phase 1: Backend and backend infrastructure

**Built (#14–#26), with these changes since:** secrets come from GitHub environment secrets through `SST_SECRET_<name>` in the deploy workflow, not `sst secret set`; the Google client IDs are public config in `infra/app/sst.config.ts`, not secrets; CORS allows any origin, since auth uses bearer tokens. [deploy.md](../deploy.md) describes the current setup.

## Context

The MVP is local-only. The backend replaces the on-device store with a real API so trips sync between people and devices.

Decisions (2026-10-24):

- **API:** Hono on Lambda behind an **API Gateway HTTP API**.
- **Database:** Aurora DSQL with Drizzle.
- **Auth:** **Better Auth**, anonymous plus Google, with users stored in our own database.
- **Realtime:** **AppSync Events**.

Every PR deploys via `main` → global → dev → production. Domain rules are reused from `@yallist/domain`.

## PR stack (each one small, each with tests, all CI green)

1. **`feat(api): Hono API on Lambda + API Gateway`**
   - **`apps/api`:** Hono app with `GET /health`, an `AppType` export for the typed `hc` client, and a Lambda handler. Vitest calls it through `app.request()`.
   - **`infra/app/sst.config.ts`:** `sst.aws.ApiGatewayV2('Api')` with a `$default` route to the function, and CORS for the web origin plus `localhost:8081`. The web build gets `EXPO_PUBLIC_API_URL`.
   - **Docs:** `docs/plans/phase-1-backend.md`, and record the three decisions in `tech-decisions.md`.
2. **`feat(db): DSQL cluster, Drizzle schema, migrations`**
   - **Cluster:** `sst.aws.Dsql('Database')` (per stage, `yallist-<stage>-…`), linked to the API, using IAM auth.
   - **Schema:** Drizzle schema for SPEC §3: profiles, trips, trip_members, items, claims, expenses, expense_shares, payments, activity and template_items. UUID keys, money in integer agorot. push_tokens and the notification-pref tables wait for the push phase.
   - **Migrations:** generated by drizzle-kit, then a small runner that applies one DDL per transaction and uses `CREATE INDEX ASYNC`, as DSQL requires. The deploy workflow runs migrations after `sst deploy`, via `sst shell`. The template seed comes from `@yallist/domain` TEMPLATES.
   - **Tests:** run against Postgres in Docker (a GitHub Actions service locally and in CI), staying within DSQL's SQL subset.
3. **`feat(auth): Better Auth with anonymous and Google sign-in`**
   - **Setup:** Better Auth on `/api/auth/*` with the Drizzle adapter, the anonymous plugin (linking to Google keeps the data), Google, and the bearer plugin. Bearer tokens, because the API and the web app are on different domains and Android has no cookies.
   - **Middleware:** `requireUser`.
   - **Secrets:** `BetterAuthSecret`, `GoogleClientId` and `GoogleClientSecret` as `sst.Secret`, per stage.
4. **`feat(api): trips, members, invites, items, claims`**
   - **Endpoints:** the SPEC §5 RPCs as Hono routes with Zod validation: create trip (from template), my trips, trip detail, preview by token (no auth), join, rotate invite, approve/decline/remove member, add/edit/delete item, set claim.
   - **Rules:** each handler checks active membership (or organizer) in the same transaction as the write, and writes the activity row there too. Claim caps use `claimCap`. DSQL write conflicts get bounded retries.
   - **Tests:** cover the SPEC Phase 1 cases: non-member can't read, pending member can't read, over-claim rejected, rotated token rejected, last organizer can't be removed.
5. **`feat(api): expenses and payments`**
   - **Endpoints:** add/delete expense with shares, linked to a buy item; mark/confirm/delete payment (confirm by the receiver only).
   - **Read side:** balances and suggested transfers come from `@yallist/domain` (`balances`, `suggestTransfers`).
6. **`feat(realtime): AppSync Events per-trip channel`**
   - **Infra:** an AppSync Events API through Pulumi `aws.appsync` resources, named per stage, with a Lambda authorizer that checks the session token and trip membership for `trips/<tripId>`.
   - **Publish:** the API publishes `{type:'changed'}` after each committed write.
7. **`feat(app): use the API instead of the local store`** (may split into 7a auth+trips and 7b items/money)
   - **Data layer:** TanStack Query with a persisted cache, the `hc` client, and optimistic claims.
   - **Screens:** login with "continue as guest" plus Google, and a working join link `/j/[token]`.
   - **Realtime:** subscribe to the trip channel and invalidate queries on events.
   - **Cleanup:** drop the demo-only bits of `state/`.

## Risks

- **DSQL in eu-central-1:** I'll verify availability in PR 2. The fallback is another EU region for production.
- **DSQL SQL subset:** no triggers or extensions, async indexes, and optimistic concurrency. That's handled in the migration runner and with retries.
- **Better Auth on DSQL:** its schema runs through Drizzle and must avoid features DSQL lacks. Fallback: a custom table mapping.
- **Cost:** DSQL free tier, about $1 per million API Gateway requests, AppSync Events about $1 per million messages; all $0 when idle.
